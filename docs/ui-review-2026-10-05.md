# Warehouse Ops UI review and implementation plan

Reviewed October 5, 2026 against the running app at `http://localhost:8081`, with supporting inspection of the current working tree. The app has a useful foundation: Work, Reports, and Lookup are understandable categories, the visual style is consistent, and most individual screens explain their purpose. The main weakness is continuity between screens. Operators can encounter conflicting readiness information, lose sight of a selected order, or reach a next-step action that does not fit the work they just completed.

**Recommendation:** start with the operator scan loop: expose the scan field on handhelds, make the current scan step explicit, clarify open versus idle work, and make expandable panels obvious. Then address selection, freshness warnings, lookup routing, and workflow handoffs. Do not consider every operational flow validated yet.

## Review scope and evidence

This was a live UI review, supported by source inspection, rather than an operational acceptance test. Browser interactions included navigation, search, order selection without submission, report filters, an allocation detail drawer, and downloading an existing Guns export. Desktop screenshots and accessibility snapshots were inspected. Today and component picking were also inspected at a 390 × 844 viewport; the viewport was reset afterward.

A temporary browser identity of `UI Review` was used to pass the operator-name prompt. No pick sessions were started, physical scans recorded, audits completed, holds acknowledged, promises changed, notifications sent, or settings saved. Read screens may perform their normal application-side refreshes. Existing uncommitted implementation changes were left intact. This document is the only repository change made for this review.

Evidence labels below distinguish **observed** behavior in the running app, **source-confirmed** implementation behavior, and **unverified** flows requiring a controlled fixture environment. Live counts and inventory can change; examples describe the review moment.

The supplemental review supplied by the user has been incorporated below as **supplied review** evidence. It reports desktop and phone checks, including an active pick session, and entry of `Tyler` as the operator on that review device. That identity change is separate from this review's `UI Review` browser identity. Its layout measurements and contrast estimates were not independently remeasured for this plan update. Overlapping findings have been merged; conflicting observations are retained as verification tasks rather than asserted as confirmed defects.

## Strengths to preserve

- Today gives a clear numbered process with status and a next action for each stage.
- Run picklist's “1. Run” and “2. Export” labels make the sequence explicit.
- The supplied active-session review reports effective autofocus and highlighting of the current pick line. Preserve those behaviors while simplifying the scan station.
- Lookup's automatic routing plus explicit alternatives is a good pattern, once identifier coverage and keyboard behavior are corrected.
- The consistent typography, restrained palette, and status colors provide a useful foundation. Improve contrast and density within that system.

## Highest priority findings

Finding numbers remain stable for implementation references. The first implementation package prioritizes findings 21, 22, 6, and 23, corresponding to the supplied review's first four issues.

### 21 Bring the scan station into the handheld viewport

**P1 · Supplied review; related mobile overflow independently observed in finding 9.** The active pick session places Pick location roughly 1.5 phone screens below the top, after an approximately 290 px header, title card, and six statistic tiles. Correct autofocus does not help when the operator cannot see the field and prompt.

Collapse session-page navigation into a compact header, reduce secondary statistics to a row of compact chips, and keep the current step, order, location, and scan field together in a sticky scan station. Put detailed totals and history below. Preserve top-of-page readiness and stale-plan warnings in a concise banner without forcing the scan field out of view. Account for the on-screen keyboard and avoid overlapping focused controls with sticky elements.

**Acceptance:** at 390 × 844 and representative handheld sizes, the initial scan prompt and active input are visible without scrolling after identity confirmation. They remain usable through step changes, error feedback, and keyboard opening. Desktop order context and current-line highlighting remain clear.

**Implementation:** `templates/pick_session.html`, `templates/_pick_lines.html`, and session-specific rules in `static/styles.css`.

### 22 Make the current scan step explicit

**P1 · Supplied review and source-confirmed.** Location, part/UPC, and serial inputs are available together. The existing code moves focus and checks prerequisites on submission, so this is an input-guidance problem rather than evidence that validation is absent. Accidental focus can still send a scanner's input to the wrong field.

Use an explicit Location → Part/UPC → Serial progression with one active capture field at a time. Prefer staged enabling of the existing inputs initially, with a clear current-step label and a deliberate Change location action. A single routed field is an alternative if hardware testing supports it. Re-enable the correct step after a failure; retain the shelf when appropriate; clear the part after an accepted unit. Keep component order/tote scanning supported. Hidden order/tote controls in the single-order flow should be omitted or explicitly non-focusable, with no unintended scanner handlers; their mere presence in the DOM is not itself a defect.

**Acceptance:** a scanner cannot accidentally enter a serial into a later or inactive step; Enter and Tab advance the intended scanner workflow; errors retain recoverable context; duplicate and fast successive scans do not skip steps. Ordinary keyboard navigation remains supported as specified in finding 10.

**Implementation:** `templates/pick_session.html` input markup and scan/focus handlers. Validate both single-order and component/tote modes.

### 1 Hidden order selection can start unexpected work

**P1 · Observed and source-confirmed.** On Guns picking, search `SO-131732`, select it, then replace the search with `ZZZ-NO-MATCH`. The table becomes empty, but the UI still says “1 of 1 selected” and enables “Start picking.” There is no visible indication of which order would start.

Keep a selected-order summary outside the filtered table, including order, customer, units, and Remove/Clear. Label the action `Start SO-131732` for a single order. Show a proper no-results state with Clear search. For components, show all selected orders and their separate totes. Preserving selections across filters is reasonable only when those selections remain visible.

**Acceptance:** changing a search cannot hide the identity of work about to start; no-match searches explain the result; the submitted order set always matches the visible selection summary.

**Implementation:** `templates/shipping.html` selection/filter script around lines 1106–1140 and the pick-start form around line 840.

### 2 Pick eligibility and data freshness are not clear across screens

**P1 · Observed; snapshot source confirmed.** `SO-131732` appears in the pick queue and can be selected, while Orders marks it BLOCKED, order detail says “no run today,” and a subsequent Stock lookup for its part reports zero pickable units. The queue uses the latest successful saved plan, dated October 2, while other screens use different snapshots or live reads. This does not prove a backend scan can bypass validation; it proves the pre-pick UI gives conflicting signals without an explanation.

**Confirmed direction:** readiness information is advisory for claiming. Any operator may claim an available order regardless of its readiness warnings. Put a clear warning summary at the top of the pick queue and relevant pick session, with the source run, generation time, age, and known readiness concerns. Defer deeper readiness review and do not add a readiness gate to the claim flow.

Stale plans also produce a warning only. Show their age and an optional link to generate a fresh plan, but keep claiming available without requiring regeneration or an acknowledgement step. Distinguish saved-plan information from current readiness/stock information so differences are understandable. Existing ownership/concurrent-claim protections and scan validation remain separate from these advisory warnings.

**Acceptance:** readiness concerns and stale-plan age are visible at the top; neither disables claiming nor requires a readiness review, regeneration, or acknowledgement. An available order can be claimed by any operator despite these warnings. Warning retrieval must not become a prerequisite for claiming; unavailable readiness information is labeled accordingly.

**Implementation:** `picklist/services/shipping_service.py:820`, `picklist/routes/pick.py:25`, queue template, shared freshness/status presentation, and readiness/stock adapters.

### 3 Lookup routes valid order identifiers to the wrong tool

**P1 · Observed and source-confirmed.** Pasting `EDI-00854`, an order visible in the pick queue, predicts Serial history and ends in “not found in the ERP.” The heuristic recognizes only numeric/SO-style orders. Component picking also contains WEB-prefixed identifiers and an order identifier shaped like a part number, so prefix guessing alone is not sufficient.

Recognize supported EDI and WEB formats. Keep explicit Open as Order/Part/Serial choices prominent. For ambiguous values, offer candidate types or a lightweight resolution step. Preserve the original value when correcting a guess. Do not silently rewrite unfamiliar identifiers.

**Acceptance:** SO, EDI, WEB, bare numeric, part, serial, and ambiguous values each resolve correctly or present an understandable choice. Keyboard users can reach the alternative choices.

**Implementation:** `templates/lookup.html:94` onward and focused identifier-routing tests.

### 4 Scheduling diagnostics contradict the configured local time

**P1 · Observed; cause requires runtime verification.** Settings displays `05:00 in America/Denver` but “Next Run” is `2026-10-05 23:00 MDT`, corresponding to 05:00 UTC. The run page agrees with the latter.

The scheduler constructs `CronTrigger(hour=hour, minute=minute)` without an explicit timezone. This is a plausible environment-dependent cause. A standalone check on this Windows host used America/Denver by default, so that check does not reproduce the running app's UTC environment or prove the full cause.

Pass the intended schedule timezone explicitly, verify the actual running process configuration, and show one authoritative next-run time. Surface a mismatch as a diagnostic rather than asking operators to reconcile several clocks.

**Acceptance:** a 05:00 Denver schedule fires at 05:00 Denver when the host is UTC or Denver, including daylight-saving transitions. UI diagnostics match the actual scheduler job.

**Implementation:** `picklist/scheduler.py:77`, `picklist/timeutil.py`, settings/run diagnostics. Test trigger calculation without firing real jobs.

### 5 Picking does not provide a complete packing handoff

**P1 · Observed and source-confirmed.** Closed-short session 13 has zero picked items but presents an emphasized “Verify a box” action. Its heading says “Gun order” without identifying the order, and it mixes `abandoned`, `closed short`, and line `released` terminology. Successful picks also hand off to a generic packlist entry rather than an order-specific next step.

Make next actions state-specific. For closed-short work, show the order, return-to-shelf requirement, and pick-queue action. For completed work, show whether the other picking team is finished, who owns packing, whether a packlist exists, and the next step. Explicitly explain the VISUAL step when packlist creation occurs outside this app. Link or prefill the associated packlist when available.

The verification start route attempts to attach a packlist to ready picks, but continues to verification when attachment returns false. Decide how standalone verification and verification of an incomplete picking workflow should be distinguished; do not infer that verification completion proves picking was finished.

**Acceptance:** closed-short work never suggests it is ready to pack; completed mixed orders show both teams' status; packlist attachment success/failure is visible; operators know which app/action comes next.

**Implementation:** `templates/pick_session.html:115`, ready-for-pack section of `templates/shipping.html`, `picklist/routes/verify.py:56`, and `picklist/stores/pick_store.py:734`.

### 6 Today does not resume all unfinished work

**P1 · Observed and source-confirmed.** Today reports “Unfinished work (0),” while Audit contains active session 337 for SHIPPING / INTERNATIONAL. The unfinished-work service includes only pick and verification sessions. The UI qualifies its empty message as pick/verification, but the broad heading and the Today promise still imply a comprehensive queue.

**Supplied review, source-confirmed:** a just-started session with 0.0 hours idle appears beneath “Flagged after 10 hours.” The service includes all open sessions and marks/sorts stale ones; it does not filter the list to ten-hour-old work. Keep all open work available for resumption and rename the panel **Open work**. Explain “All in-progress sessions; highlighted after 10 hours without a scan or order action.” Mark stale rows with an explicit Needs review badge and show separate total/stale counts.

Include active audits with target, operator, age, progress, and Resume. Also surface overdue audit locations as due work, separately from already-started sessions. Collapse an empty summary so it does not push real work down the page. Query active work directly rather than deriving completeness from a capped recent-history list. Finding 23 covers the panel's expansion affordance.

**Acceptance:** a new session appears as In progress without implying it is stale; the ten-hour boundary controls its Needs review indicator; an active audit remains visible regardless of newer sessions; overdue audit locations have an action without being counted as open sessions; abandoned work is not mistaken for completed work.

**Implementation:** `picklist/services/unfinished_work.py`, `picklist/routes/shipping.py:70`, `templates/_unfinished_work.html`, `templates/work.html`.

## Visual and wording refinements

Keep the current theme and major navigation groups. It is already readable on desktop and does not need a wholesale redesign. Concentrate on denser work screens, meaningful status labels, and clearer action hierarchy.

- Consider making Today the default entry point at `/`, while retaining a stable Run picklist route and redirect for existing bookmarks. The current root opens the run console rather than the daily work overview.
- Use one shared operator identity editor as described in finding 25, with a compact name/team chip on handhelds and an explained reconfirmation prompt.
- Translate raw states into a small vocabulary: Picking, Ready for packing, Awaiting other team, Closed short, Verification cancelled, Verified clean, Needs review. Explain who owns the next step.
- Give queues readable customer names with identifiers as secondary text. Hide redundant all-zero columns in type-specific picking views.
- Change blanket claims such as “every extra box is avoidable” to “potential consolidation savings”; legitimate splits are already acknowledged elsewhere on the page. Likewise, label transfer candidates for review when stock appears in held, quality, engineering, or consignment locations instead of implying every source is freely transferable.
- Replace empty tables after filtering with “No matching results,” the active filters, and Clear. Retain density controls where they are useful, but apply them consistently.
